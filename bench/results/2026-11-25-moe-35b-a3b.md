# Qwen3.6-35B-A3B on the iGPU: is it worth targeting? (2026-11-25)

On AC, platform profile `balanced`, iGPU 890M, our llama.cpp 6b0f75b (Vulkan, fa on).
`Qwen3.6-35B-A3B-UD-Q4_K_M.gguf` (20.6 GiB; arch `qwen35moe`: 40 layers, hybrid linear /
full attention, 256 experts, 8 active, hidden 2048) and the `-MTP-` variant (+1 nextn layer).

| | 35B-A3B | Qwen3-8B Q4_K_M (for comparison) |
|---|---|---|
| prefill (llama-bench pp512) | 471 tok/s | ~430 tok/s on the NPU (packed, T-033) |
| decode, 1 sequence (tg64) | **20.9 tok/s** | 15.3 |
| decode, 2 sequences total (batched-bench) | 30.5 | 29.5 |
| decode, 4 sequences total | 40.8 | 54 |

MTP (llama-server `--spec-type draft-mtp`, its default draft length, greedy, 256 tokens,
thinking off): code 20.7 → **31.9 tok/s** (183/213 drafts accepted); story 20.6 → 19.8
(139/346 accepted: a fixed draft length loses on prose, the case BatchK handles).

Reading: a much stronger model that is also faster than the 8B for 1–2 concurrent requests
(MoE: 3B active per token; batching helps less, as tokens use different experts). With an
adaptive MTP draft: ~32 tok/s on code single-stream (8B + 0.6B draft: 27.4).

What adopting it in xdna-relay needs (not started):
- Recurrent (linear-attention) state cannot be truncated: speculative rollback and the prefix
  cache need state checkpoints (llama.cpp has them for its server; our shim does not expose
  them; `prefix_cache.prepare` currently falls back to a full reset).
- MTP draft through the shim (llama.cpp's draft-mtp path) and BatchK over it.
- NPU prefill: a new IRON graph (gated linear attention + MoE experts): large; the iGPU's
  471 tok/s prefill already beats our 8B NPU prefill, so the NPU's value here is only
  keeping the iGPU free for decoding during long prompts.
